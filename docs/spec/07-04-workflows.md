### 7.4 Workflows (`.github/workflows/`)

Three files. Two environment variables, `OPENUI_TELEMETRY_DISABLED=1` and `DO_NOT_TRACK=1`, are set in `ci.yml` and `release.yml` because OpenUI's install script sends telemetry otherwise.

**`ci.yml`, workflow "CI"**, runs on every pull request and on pushes to `main` (a branch push without a PR runs nothing). `concurrency` groups runs by PR: a newer push cancels the PR's older run; runs on `main` always finish. `permissions` gives the token read access only (`contents: read`, `pull-requests: read`), whatever the repository's default. Every job has a `timeout-minutes` limit (5 to 15 minutes) instead of GitHub's 6-hour default, and every checkout sets `persist-credentials: false`, so the token is not left in `.git/config` for later steps (npm and pip install scripts, the test scripts): no step uses git with it. Jobs, all on `ubuntu-latest`; the slow ones only run when the change needs them, and a skipped job counts as passed for the `main` ruleset:

| Job | Name in the Actions list | Steps |
|---|---|---|
| `changes` | What changed | On a PR, first runs `tools/check-attribution.sh` on the PR's commits (from the GitHub API) and fails when one credits an AI tool, which fails the required `web` check too. Then gets the PR's file list (`gh pr diff --name-only`) and pipes it through `tools/ci-changes.sh`, which prints `web=`, `contract=` and `patches=` outputs; on `main`, or when the list can't be read, everything is `true`. |
| `web-unit` | Web typecheck and unit tests | Only when `web` is true. Node 22 with npm cache; `npm ci`, `npm run typecheck`, `npm test` in `web/`. |
| `web-e2e` | Web build and browser e2e (01-06), (07-11), (12), (13-16,19-), (17-18) | Only when `web` is true, in parallel with `web-unit`: a matrix of five shards (`fail-fast: false`; spec 7.3 says why these), each on its own runner. `npm ci` and `npx vite build` in `web/` (the typecheck is in `web-unit`); caches Playwright's browser in `~/.cache/ms-playwright` keyed on the e2e lockfile; in `tools/web-e2e`: `npm ci`, `npx playwright install chromium` (without `--with-deps`: the runner image already has the system libraries, and the `apt-get` run it starts took about 20 s per shard), `./run.sh --only <shard>` with `HM_E2E_SKIP_BUILD=1`. The shard list is in the matrix; `tools/check.sh` reads it from there. |
| `web` | Web (typecheck, unit tests, build, browser e2e) | The name the `main` ruleset requires. Runs always (`if: always()`) after `changes`, `web-unit` and `web-e2e`; fails if any of them failed or was cancelled, passes when they passed or were skipped. |
| `plugin` | Plugin (canvas + media) | Python 3.12; `pip install fastapi httpx`; runs `test_canvas.py`, `test_library.py`, `test_gallery.py`, `test_media.py`, `test_chat_search.py`, `test_checkpoints.py`, `test_battery.py`, `test_approval.py`, `test_chip.py`, `test_phone_app.py`, `test_auto_mode.py`, `test_openui.py`, `test_openui_query.py`, `test_claude_login.py`, `test_phone_access.py`, `test_profile_link.py`, `test_sent_counts.py`, then `python3 tools/test_check_spec.py` and `python3 tools/check_spec.py` (the second one fails the build when the code has a name `docs/SPEC.md` lacks), then `python3 tools/test_changelog.py` and `python3 tools/changelog.py check`. |
| `hermes-patches` | Hermes patches apply to the pinned Hermes | Only when `patches` is true (Hermes patches, the pin, `phone/`, the shell scripts in `tools/`; a docs-only PR skips it, which the ruleset counts as passed). `tools/test_hermes_patches.sh`, then `test_hermes_debian.sh`, `test_bootstrap_pin.sh`, `test_bootstrap_image.sh`, `test_say_hook.sh`, `test_install_routes.sh`, `test_uninstall.sh`, `test_hm_shizuku.sh`, `test_device_lock.sh`, `test_ci_changes.sh`. |
| `android` | Android Java compiles | Temurin JDK 21; caches `~/.cache/hermes-mobile` (key `android-all-16`); `tools/java-check.sh` (which checks the jar's SHA-256 and also runs `test_shizuku_keeper.sh`), `tools/api-check.sh`, `tools/test_setup_lines.sh`, `tools/test_autostart.sh`, `tools/test_devtools_guard.sh`. |
| `hermes-contract` | Mock Hermes matches the pinned Hermes | Only when `contract` is true. Node 22 with npm cache, `astral-sh/setup-uv` with its cache keyed on the Hermes pin; `npm ci` in `tools/web-e2e` (no browser download), then `tools/hermes-contract/run.sh "$RUNNER_TEMP/hermes-contract"` (it also uses the runner's `python3` for the fake model). 15-minute limit; a run takes about 3 minutes (127 cases). |

Not in CI: `e2e.py` and the other phone tools, `test_bghost.sh`, `tools/web-e2e/coldstart.cjs`.

**APK workflow retained:** `build-taher.yml` builds, verifies, uploads, and publishes the signed Hermes Taher APK in one workflow. The redundant original-app `release.yml` and candidate `apk-candidate.yml` were removed. Non-APK CI, upstream monitoring, and Debian-image workflows remain intact.

**`image.yml`, workflow "Ready-made Debian image"**, manual only (`workflow_dispatch`, input `publish`, default false). Run it after moving the Hermes pin in `phone/bootstrap.sh`. One job `image` on `ubuntu-24.04-arm`, 90 min limit, `contents: write`, checkout with `persist-credentials: false`:
1. Runs `test_bootstrap_pin.sh` and `test_bootstrap_image.sh`.
2. Installs `zstd`; runs `tools/build-image.sh image-out`; checks `sha256sum -c`.
3. Computes the file name (`build-image.sh --name`) and the release tag `hermes-image-<first 12 of the pin>`.
4. If `publish` is off: uploads the image, its `.sha256` and `build.log` as a workflow artifact (7 days). If on: creates the release `hermes-image-<pin12>` when missing (prerelease, `--latest=false`, so the app's update check and the APK download keep pointing at the app release), then uploads the image first and the `.sha256` second (a half-replaced pair fails `bootstrap.sh`'s hash check, which falls back to a normal install).

Additional GitHub Actions workflows: `build-taher.yml` builds and publishes the Taher app on main app changes; `watch-upstream.yml` checks upstream changes. Changes merged into `main` do not themselves publish an APK. The original `release.yml` was removed; integrations must not create release tags automatically.

**Hermes Taher 1.0.15 candidate.** `build-taher.yml` also runs on `main` changes to Android, web, phone, and its own workflow file. It builds version `1.0.15` with versionCode `100015`, signs with the existing Taher keystore, verifies the APK and uploads `hermes-taher-1.0.15-apk` as a workflow artifact. This is a build artifact, not a published GitHub release. Subsequent builds intended for installation must increment versionCode.

**Unified Taher APK delivery:** `build-taher.yml` is the only APK workflow. Changes to app code on `main` trigger the signed production build, signature verification, artifact upload, and GitHub Release publication in sequence. Version `1.1.<run_number>` uses versionCode `110000 + run_number`, which stays above the previous `1.0.15` (100015). Releases are named `taher-v1.1.<run_number>` and include `Hermes-Taher-1.1.<run_number>.apk` and its SHA-256 checksum. The in-app updater checks the repository's latest GitHub Release. `release-taher.yml` has been removed.

`build-taher.yml` rejects a signed production APK when `aapt2 dump resources` contains `hm_devtools`, before uploading or publishing it. `test_devtools_guard.sh` checks this current production workflow rather than the removed `release.yml`.
